## Befund (Diagnose)

### 1. 500er auf /tasks — mutmaßliche Ursache
- Keine fehlenden Stammdaten: 409 tasks, 5 statuses, 4 priorities, 19 types, 14 projects, 43 users vorhanden.
- Keine dangling FKs (parent/status/creator/active_user alle sauber).
- Kein kaputer Import in datasource.ts (UserCurrentActiveProject statt UserRole, UserSubRole vorhanden).
- Hauptverdacht: tasks/+page.server.ts load() macht 6+ schwere Relation-Queries (Task+tag+project+usertask+timeentry+projectuser) mit SELECT DISTINCT/ORDER BY LIMIT 1; bei Hydration kombiniert mit der AppState-Flackerei wirft der Load oder die hydration. Exakter Stack braucht Live-Login-Reproduktion.

### 2. App-Masken-Flackern (bestätigt)
- +layout.svelte gated komplette Maske hinter {#if browser}{#if user}{#if appState.current === main}.
- appState.current startet hart als "landing"; init() liest localStorage NUR im if(browser), aber data.appState aus +layout.server.ts (cookie) wird NIE in store zurueckgeschrieben.
- Folglich: Refresh auf /tasks => current="landing" => Guest/Fallback-Branch statt Maske, erst nach Reaktion springt main-Branch (die ~5s).

### 3. State-Architektur (bestätigt)
- Import-Pfadfehler: 4 Dateien importieren $lib/state.svelte.js, Datei heisst aber state.svelte.ts (.js existiert nicht).
- Doppelter Store: state.svelte.ts (AppState) UND stores/appState.svelte.ts (AppStateStore) tun dasselbe.
- kanban-store.svelte.ts importiert writable aus svelte/store (Svelte-4) obwohl $state genutzt.
- [404] GET /avatars/admin.jpg => fehlender Avatar-Asset (Seed-/Asset-Problem, nicht 500-Ursache).

### 4. Performance-Bombe (bestätigt)
- Jede Navigation wiederholt Session+User+Role+UserCurrentActiveProject+Project(+relations)+Lookups (siehe Container-Logs: riesige SELECT DISTINCT Subqueries).
- 409 Tasks werden voll hydriert (Task+taskStatus+priority+creator+user+parent+taskType) + separate Tag/ProjectTask/UserTask/TimeEntry-Queries => N+1.
<!-- SECTION:NOTES:END -->
